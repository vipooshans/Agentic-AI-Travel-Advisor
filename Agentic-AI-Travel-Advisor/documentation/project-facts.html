Agentic AI Travel Advisor

C. Both React and ASP.NET MVC are implemented.

  • React: web-react. React 19.3 (react ^19.3.0), Vite, React Router 7.
  • State management: React Context (AuthProvider / AuthContext) plus local component state. Not Redux, Zustand, or a global store.
  • ASP.NET MVC staff portal: web-app, also implemented. It is a second UI for admin, owner, and agent. It does not replace React.
  • React URL if deployed: Not deployed. Local only: http://localhost:5173 (npm run dev), preview http://localhost:4173.

Main React pages:

  • Public: Home, Login, Register, Hotel detail, Package detail, Forbidden, Not found.
  • Traveler: Assistant, My bookings, Itineraries, Profile.
  • Hotel owner: Dashboard, Hotels, Rooms, Bookings.
  • Travel agent: Dashboard, Packages, Package activities, Transport, Bookings.
  • Admin: Dashboard, Approvals, Users, Destinations, Bookings, Reviews, Settings.

2. AI agents

Four specialised agents exist. The fourth is already BookingAgent, not a renamed prompt.

  • Agent 1 — TravelPlanningAgent. Reads the chat and saved preferences. Extracts destination, dates, duration, travelers, budget (LKR), interests, accommodation and transport. Asks a clarifying question if destination or budget is missing.
  • Agent 2 — RecommendationAgent. Searches the approved catalog, picks a budget-compliant hotel/room/package/transport combination, and checks live availability.
  • Agent 3 — ItineraryAgent. Turns that selection into the day-by-day plan, cost breakdown, and reply. Validates the plan against TravelPlanSchema.
  • Agent 4 — BookingAgent. Builds a priced booking proposal. Creates a booking only after the traveler explicitly confirms. The booking stays Pending until the provider confirms it.

Orchestrator: AgentOrchestrator. Tools: search destinations, hotels, packages, activities, transport, check availability, get preferences, generate itinerary, create booking. OpenAI-compatible tool calling when Ai:ApiKey is set; otherwise the same agents run deterministically.

3. Human approval

YES.

AI plan is validated, then two people must agree before a stay is confirmed:

  • Traveler must confirm the proposal (reply “confirm”, or the confirm id). Nothing is booked before that. The proposal expires (default 15 minutes).
  • Hotel owner confirms a room booking. Travel agent confirms a package booking. An administrator can also change booking status.

Separate from the chat: new and edited hotels and packages stay Pending until an administrator approves them. Unapproved listings are hidden from search, the AI tools, and booking.

There is no extra “admin approves the AI text” step. Approval is the traveler’s confirmation of the proposal, then the provider’s confirmation of the Pending booking.

4. AI workflow state

PARTIALLY.

Saved in PostgreSQL:

  • AIConversations.Id (conversation id, not a separate workflow-run id)
  • User message (the objective) and assistant reply, inside Messages JSON
  • Plan, status, pending booking proposal, and created booking id, on that JSON message
  • AIRecommendations: item, estimated cost, score, reason, conversation id
  • A saved itinerary can store budget, travelers, and the source conversation id

Not stored as their own columns or tables: agent step log, tool-call results, schema validation result, and errors. Those are returned on the live ChatResponse (agents, toolCalls, status) and are not copied into ChatMessageDto.

5. Third-party API / service

  • Third-party service: OpenAI-compatible chat API. Default https://api.openai.com/v1, model gpt-4o-mini. Ai:BaseUrl can point at another compatible host.
  • Purpose: LLM tool-calling for the travel assistant. If no API key is set, or the provider fails, the deterministic agents still produce a plan from the catalog.
  • Where integrated: Backend (OpenAiCompatClient in Infrastructure). React and Flutter only call POST /api/ai/chat.

Unsplash URLs are static image links in seed data, not an API client. Card payment is a simulated gateway inside the API (test card 4000 0000 0000 0002 is declined). Card numbers are not stored. There is no Google Maps, weather, email, SMS, or cloud-storage client.

6. Flutter device feature

Date and time selection. The booking screen uses Flutter showDatePicker for check-in and check-out (create_booking_screen.dart).

GPS, maps, image picker, QR, push notifications, and file upload are not in the Flutter code.

Flutter state: the provider package (AuthProvider, ChatProvider, both ChangeNotifier).

ConstraintsYes. CHECK constraints (price, capacity, dates, rating), foreign keys, unique indexes, and EX_Bookings_Room_NoOverlap (GiST exclusion so one room cannot be double-booked).
TransactionsYes. UnitOfWork.ExecuteInTransactionAsync. Booking creation locks the room or package row inside a transaction.
CreatedAt / UpdatedAtYes, via IAuditable and AuditInterceptor. Not on Identity’s extra tables, Roles, or ItineraryItems.

Relationships (from the EF model and DATABASE.md)

  • User → Role. User 1:1 UserProfile. User 1:1 TravelPreferences.
  • Hotel owner (user) 1:N Hotels. Hotel 1:N Rooms. Room 1:N RoomAvailability.
  • Destination 1:N TravelPackages. Travel agent (user) creates packages. Package 1:N PackageActivities.
  • Transportation belongs to an agent, and may point at a package and a destination.
  • Booking belongs to a user and to exactly one of Room or TravelPackage. Booking 1:N Payments. Booking 1:1 Review (completed bookings).
  • Review points at a hotel or a package.
  • User 1:N AIConversations. Conversation 1:N AIRecommendations (hotel, room, package, transport, or destination). User 1:N Itineraries. Itinerary 1:N ItineraryItems. Itinerary may point at a destination and a conversation.
